# FinOps, Versioning, and Production Judgment for AI/ML/LLM Systems

The other files in this folder cover the tooling landscape and the reliability/debugging practices underneath it. This file covers what's left: the *money and infrastructure* side (costing, token management, FinOps), the *versioning* side (models, endpoints, data), the *lifecycle* side (dev→prod, CI/CD, maintenance), and — the part no textbook page can teach by itself — **judgment**: how to take an ambiguous, half-specified operational problem and actually work through it, reasoned out loud, the way you'd have to in a real incident.

Same rule as the rest of this folder: checked against what a real production AI stack's code actually does and what this project's hands-on stack actually runs, not generic textbook answers. Where something is aspirational rather than real, it's labeled as such.

## 1. AI infrastructure: management and costing

"AI infrastructure" for an LLM-based product (as opposed to a classical ML shop training models from scratch) breaks into three cost centers that behave completely differently and get confused constantly:

1. **Inference cost (the recurring, usage-scaling one)** — every token generated by a hosted model (OpenAI, Anthropic, Bedrock) or every GPU-second spent running a self-hosted model costs money *per request*. This is the cost that scales with product usage, and it's the one that can silently blow up a budget because nobody notices until the bill arrives — there's no equivalent of a server falling over to force attention onto it.
2. **Training/fine-tuning cost (the occasional, batch one)** — GPU-hours spent on a training or fine-tuning job. Bursty, predictable in advance (you know before you kick off a job roughly how long it'll run), and easy to budget for because it's a discrete event, not a continuous drain.
3. **Standing infrastructure cost (the fixed one)** — vector databases, feature stores, GPU instances kept warm for low-latency serving, observability stacks (Langfuse/Grafana/Prometheus all have real infra costs at scale — ClickHouse and object storage aren't free once trace volume is real). This is the cost that exists whether or not anyone uses the product that day.

**The management decision underneath all three**: managed vs. self-hosted, and it's not a one-time choice — it's a per-workload decision.

- **Managed (OpenAI API, Bedrock, a hosted vector DB)** — no infra to run, pay per unit of usage, scales to zero when idle, but you're paying a margin on every token/query and you're at the mercy of the provider's rate limits, pricing changes, and availability.
- **Self-hosted (Ollama/vLLM on your own GPUs, a self-run Qdrant/Chroma/Weaviate cluster)** — fixed cost whether used or not, someone owns the operational burden (patching, scaling, GPU driver hell), but at high, steady volume it gets cheaper than paying per-token forever, and you get full control over data residency and latency.

The crossover point is a real number, not a vibe: if `(self-hosted fixed cost) < (managed per-unit cost × expected volume)`, self-hosting wins on a pure cost basis — but that ignores the operational cost of *someone having to run it*, which is real and easy to under-price (see §11 on reliability/observability — a self-hosted model or vector DB is now a service *you* have to keep alive, not the provider).

**The hardware question underneath all three cost centers**: which processor a workload actually runs on (CPU/GPU/TPU/NPU) drives both the standing-infra cost and the achievable latency at a given traffic volume — see `01-foundational-ai-ml.md` §9 for what each one is and a stage-by-stage table (training vs. fine-tuning vs. serving-at-scale vs. serving-small vs. on-device) for which hardware actually fits which workload, including this project's own CPU-only Ollama setup as a lived example of exactly where that choice stops being viable.

**Where this project shows it concretely**: [`../../services/llm-gateway`](../../services/llm-gateway) runs *both* — Ollama (self-hosted, local, free-per-token but the machine's own CPU/RAM is the real cost, as this project's own Docker resource crisis demonstrated directly) and a fallback chain to hosted providers, unified behind one interface. [`../../services/llm-gateway/app/main.py`](../../services/llm-gateway/app/main.py)'s provider fallback chain is exactly the mechanism that lets you route by cost/latency/availability instead of hardcoding one provider — the same architectural piece a real cost-management strategy needs, whether or not cost-based routing logic exists yet.

**It's common for a real org's actual position to look like this**: hand-rolled LangChain agents calling provider SDKs directly, no unified gateway, no MLflow/feature-store/Kubeflow anywhere. In that scenario, cost visibility is wherever each individual repo's provider calls happen to log it (if at all) — there is no single place to answer "what did our LLM usage cost this month, broken down by product surface." That absence *is* the finding, and it's the first thing worth fixing before any FinOps practice (§3) can exist at all, because you can't manage what you can't see in one place.

## 2. Token management as an operational discipline

Tokens are the unit LLMs actually bill and reason in (see `01-foundational-ai-ml.md` §2 for what a token is). "Token management" is the set of practices that keep token usage bounded, predictable, and cheap — three different failure modes, three different fixes:

1. **Context window overflow** — a conversation, plus retrieved RAG context, plus tool-call results, plus system prompt, exceeds the model's context window. The naive failure mode is a hard error; the *dangerous* failure mode is silent truncation that drops something load-bearing (the system prompt's safety instructions, or the one retrieved chunk that actually answered the question) without anyone noticing. Management here means: track token count *before* sending, not after failing; truncate deliberately (oldest conversation turns first, usually) rather than let the API do it for you; and budget context deliberately — the system prompt + tool definitions + retrieved context + conversation history all compete for the same window, and a bloated system prompt or an over-fetching RAG step steals room from conversation history that might matter more.
2. **Cost-per-request creep** — a system prompt or a tool-definition schema that grows over time (every bug fix adds "also don't do X" to the prompt) silently multiplies the cost of *every single request* forever, forwards, not just the request that needed the fix. This is the single most common way LLM cost creeps upward without any usage growth at all — worth auditing system-prompt length over time the same way you'd audit a slow memory leak.
3. **Uncontrolled generation length** — a model that isn't told to be concise, or isn't given a `max_tokens` cap, will sometimes generate far more than needed, and you pay for output tokens too (usually at a *higher* per-token rate than input tokens across every major provider). Capping `max_tokens` isn't just a safety net against runaway loops — it's a direct cost control.

**Where this project demonstrates it**: [`../../services/llm-gateway`](../../services/llm-gateway) sits as the single choke point through which every LLM call in this stack passes — which is exactly the architectural position token management needs, because it's the one place that can enforce a cap or truncation policy regardless of which upstream service (agent-service, eval-service, a future service) originated the call, without each of them having to reimplement the same logic. Whether that enforcement exists today is a separate question from whether the *position* to enforce it exists — check [`../../services/llm-gateway/app/main.py`](../../services/llm-gateway/app/main.py)'s request-building code directly rather than assuming.

## 3. FinOps for AI systems: token cost, compute cost, infra cost, and how they interact

FinOps (a cloud/finance-ops discipline generally) applied to AI systems specifically means: making the cost of an AI feature *visible, attributable, and boundable* before it becomes a surprise line item. Three practices, in the order most teams actually adopt them (cheapest first):

1. **Tagging and attribution** — every LLM call should be attributable to a product surface, a customer/tenant, and ideally a specific feature. Without this, "our OpenAI bill went up 40% this month" has no next question you can ask — you can't tell if it's one noisy tenant, a new feature, or a bug causing retry storms. The cheapest version of this is just structured logging with consistent labels; the mature version is a cost-allocation dashboard, which is exactly what a unified gateway (§1) makes possible and a scattered set of direct-provider-SDK calls (a common real-world starting state) makes nearly impossible.
2. **Budgets and alerts, not just dashboards** — a dashboard you have to remember to check catches nothing in real time. A budget alert (Prometheus/Grafana can do this the same way it'd alert on error rate — see §11) that fires when hourly/daily token spend crosses a threshold is what actually catches a runaway loop or a misconfigured retry policy before it becomes a five-figure surprise. This is the FinOps equivalent of an SLO alert, and it deserves the same seriousness.
3. **Cost-aware routing** — once cost is visible per-request, you can route on it: cheaper/smaller models for easy classification tasks, the expensive frontier model reserved for the turns that actually need it. This is the same pattern as this project's urgency classifier (a small, cheap, purpose-built sklearn model — not an LLM call at all) triaging *before* the expensive conversational LLM turn happens; classification-shaped subtasks almost never need a frontier model, and routing them to one is pure waste.

**The interaction that catches teams off guard**: compute cost and token cost trade off against each other, not independently. A self-hosted model (compute cost, fixed) removes per-token cost entirely but only if utilization is high enough to justify the fixed spend — an idle GPU instance costs the same whether it serves one request or ten thousand. This is exactly the crossover-point math from §1, and it's why "just self-host it, tokens are expensive" is not automatically the right call — it's a volume-dependent answer, and getting the volume estimate wrong in either direction is the actual risk, not the infrastructure choice itself.

**Concretely, what a FinOps review for an LLM feature should ask, in order**: (1) what does this cost per request today, broken down by input tokens / output tokens / any tool-call round-trips; (2) what's the expected volume at current and 10x scale; (3) does a cheaper model or a smaller context window solve this just as well; (4) is there a budget alert that fires before this becomes a monthly-bill surprise. If you can't answer (1) with a real number rather than an estimate, that's the actual gap to close first — everything else is premature.

## 4. Model & endpoint versioning, as an ops discipline

`02-llmops-mlops-tooling.md` §5 covers MLflow as a tool; this is the *practice* MLflow (or any model registry) exists to serve, and it applies whether or not you have MLflow running.

**The core problem versioning solves**: a model in production is not a fact, it's a pointer — and if that pointer isn't explicit, versioned, and independently movable from a code deploy, then "which model is live right now" becomes a question only answerable by asking whoever deployed it last, which doesn't scale past one person's memory (the exact failure mode [`../../services/mlflow/README.md`](../../services/mlflow/README.md) opens with, describing a real gap common at orgs like this).

Three things a real versioning practice needs, all demonstrated live in this project:

1. **Independent versioning from code.** A model artifact should be versionable and promotable without a code deploy — [`../../services/mlflow/train_and_log.py`](../../services/mlflow/train_and_log.py) registers a new model version via `mlflow.pyfunc.log_model(...)`, completely decoupled from `agent-service`'s own deploy cycle. `agent-service` polls for whichever version is aliased `champion`; promoting a new model version is a registry operation, not a redeploy.
2. **A named, moveable pointer (alias), not a hardcoded version number.** `champion`/`challenger` aliases (MLflow's own terms) mean promotion = moving a pointer forward, rollback = moving it back — no redeploy, no code change, and (critically) no ambiguity about which specific artifact is "the one in prod" at any given moment, because the alias *is* the answer.
3. **A tested rollback path, not just a theoretical one.** `train_and_log.py`'s own walkthrough deliberately trains a *worse* candidate, promotes it, measures the regression, and rolls back automatically — proving the rollback mechanism works before you ever need it under real pressure. A rollback path nobody has actually exercised is a rollback path you don't actually have; find out it's broken during an incident, and you've turned a model regression into a longer outage.

**Endpoint versioning specifically** (as distinct from model versioning) is the same idea one layer up: if a service's *API contract* changes (a new required field, a changed response shape), that's a versioning event independent of which model is behind it. A model can be swapped with zero API change (same input/output shape, better weights); an API contract change can happen with zero model change (a new field added to the response). Conflating the two — treating "we shipped a new model" and "we shipped a new API version" as the same kind of event — is a common source of confusion about what actually needs a version bump, a changelog entry, or a client migration.

**The gap worth naming plainly**: it's common for an org like this to have no model registry anywhere today — which means the "which version is live, how do I roll back" question currently has no answer beyond someone's memory of which file/branch/S3 object was deployed. This is precisely the gap this project's MLflow setup exists to demonstrate closing, concretely, with a live consumer (`agent-service`) proving the mechanism actually changes production behavior — not a registry-bookkeeping demo.

## 5. Data versioning

Model versioning (§4) answers "which weights are live." Data versioning answers a different, equally important question: "what data produced this model, and can I reproduce it?" Three distinct things get called "data versioning" and they solve different problems:

1. **Training-data versioning** — snapshotting the exact dataset (rows, labels, preprocessing) that produced a given model version, so a model's behavior is reproducible and auditable. Tools like DVC (Data Version Control) or lakeFS exist for this specifically. Without it, "why did the model's behavior change" has no answer beyond "we retrained it on... something" — the same un-auditability problem model versioning solves, one layer upstream. This project's [`../../services/mlflow/train_and_log.py`](../../services/mlflow/train_and_log.py) logs the training data inline as a versioned parameter/artifact of the run itself (small enough here to embed directly) — the same principle DVC applies at real scale, just via MLflow's own artifact store instead of a dedicated data-versioning tool.
2. **Feature versioning** — a feature store's actual job (see `01-foundational-ai-ml.md` §5): guaranteeing the *definition* of a feature (not raw data, a computed value) is identical between training and serving, and that changing the definition is itself a versioned, trackable event, not a silent edit to a SQL query somewhere. [`../../services/feature-store/`](../../services/feature-store/) (Feast) demonstrates exactly this — `feature_repo/features.py`'s `FeatureView` schema is the versioned definition; changing it (as happened when `open_tickets` was added to make the urgency classifier a real, live consumer) is a deliberate, visible schema change, not an invisible one.
3. **Embedding/index versioning** — the one people forget. If the embedding *model* changes (a new version of `all-MiniLM-L6-v2`, or switching providers entirely), every previously-stored vector in the vector DB is now numerically incompatible with freshly-embedded queries — same text, different vector space, silently wrong similarity scores with no error thrown anywhere. This has to be tracked as a versioned event tied to a full re-index, not treated like a routine model upgrade. [`../../services/rag-service`](../../services/rag-service) pins its embedding model explicitly for exactly this reason — bumping it without a full re-embed of the existing knowledge base would silently degrade retrieval quality with zero visible error.

**The practical rule underneath all three**: if you can't answer "what exact data/definition/embedding-model produced the thing currently in production, and could I reproduce it from scratch," you don't have data versioning, you have data that happens to still exist. Reproducibility is the test, not "is there a copy somewhere."

## 6. Vector DBs, and all the databases — the full data-store landscape

`01-foundational-ai-ml.md` §4 covers what a vector DB *is* (embeddings, cosine similarity, ANN/HNSW indexing) and audits a real org's typical footprint (mostly dead scaffolding — see that section for the Weaviate/pgvector findings). This section is the wider map: a real AI system almost never runs on just one kind of database, and knowing which kind of data belongs in which store is a load-bearing architectural decision, not a preference.

| Store type | What it's for | Example in this stack | Get this wrong and... |
|---|---|---|---|
| **Vector DB** | Semantic similarity search over embeddings | ChromaDB in `rag-service` | you either brute-force search (slow past tens of thousands of vectors) or store embeddings in a store with no ANN index and eat a full scan every query |
| **Relational (Postgres)** | Structured, transactional, relationship-heavy data — the model registry's metadata, Langfuse's org/project/API-key records | `postgres` (MLflow), `langfuse-db` | you lose ACID guarantees exactly where you needed them (billing records, access control), or you force-fit unstructured data into rows and fight the schema forever |
| **Columnar/analytical (ClickHouse)** | High-volume, append-heavy, aggregation-query-heavy data — traces, observations, scores at real production volume | `langfuse-clickhouse` | a relational DB falls over under trace-ingestion volume long before a columnar store would, because row-oriented storage is the wrong shape for "count traces by hour over the last 30 days" style queries |
| **Object storage (S3-compatible)** | Large blobs — model artifacts, media attached to traces, training datasets | `langfuse-minio` (S3-compatible), MLflow's artifact store | you stuff large binary blobs into a relational DB's row, which works until it doesn't (backup size, query performance, replication cost all degrade) |
| **Cache/queue (Redis)** | Fast ephemeral state, and async job queues between services | `langfuse-redis` (both — cache *and* the queue `langfuse-worker` consumes from) | you either hit your primary DB for data that doesn't need durability, or you build a queue out of polling a table, which is slower and harder to reason about than a real queue |
| **Feature store** | Versioned ML input variables, served identically offline and online | `feature-store` (Feast) — see §5 above | train/serve skew (§5, and `01-foundational-ai-ml.md` §5) |
| **Time-series (implicit here via Prometheus)** | Metrics — a value plus a timestamp, queried by rate-over-time, not by primary key | Prometheus's own TSDB, feeding Grafana | jamming metrics into a relational table works until you need "rate of change over the last 5 minutes," which a time-series DB answers natively and a relational one answers via increasingly painful window functions |

**The judgment call this table is really testing**: when a new data need shows up, the question is never "which database do we already have running" (that's how you end up with dead pgvector scaffolding, per `01-foundational-ai-ml.md` §4) — it's "what access pattern does this data actually need," and the answer usually picks the store type for you. Semantic similarity → vector DB. Transactional consistency on structured records → relational. High-volume append + aggregate queries → columnar. Large binary blobs → object storage. Ephemeral fast state or async decoupling → cache/queue. A store that's already running but wrong for the access pattern is worse than provisioning a new, correct one — it just fails later and more confusingly.

## 7. Dev → prod pipeline and maintaining AI workloads

An AI workload's dev→prod path has one structural difference from a normal service's: **the model/prompt/retrieval-config is a deployable artifact independent of the code**, and a pipeline that only versions code misses the half of the system most likely to change.

A workload-aware pipeline needs stages for both:

1. **Code path** (same as any service): lint/type-check → unit tests → build → deploy. Nothing AI-specific here.
2. **Model/config path** (the part a normal CI/CD pipeline doesn't know exists): train/tune → offline eval against a held-out set (`eval-service`'s job) → register in a versioned registry (§4) → promote via alias, gated on the eval passing a threshold, *not* gated on a code deploy succeeding. [`../../services/mlflow/train_and_log.py`](../../services/mlflow/train_and_log.py)'s baseline→candidate→compare→rollback sequence *is* this stage, compressed into one runnable script for teaching purposes — a real pipeline would trigger it on a schedule or on new training data landing, not run it by hand.
3. **Live monitoring, post-promotion** (this is "maintenance," not "deploy" — an AI workload doesn't stop needing attention once it ships): sampled online eval (§ "Closing the gap" in `03-reliability-debugging-ops.md` §3) catching quality regressions live, drift detection (are live inputs starting to look statistically different from training data — a classic silent-failure mode with no error thrown anywhere), and the same golden-signal monitoring any service needs (§11) plus AI-specific signals (§10 in `03-reliability-debugging-ops.md`).

**The maintenance burden that's easy to under-budget**: an AI workload degrades even with zero code changes, in a way a traditional service mostly doesn't — the world the model was trained on drifts (new slang, new product features customers ask about, a competitor's outage changing what "urgent" support messages look like), and nothing in a standard CI/CD pipeline notices this by default. This is why "ship it and it's done" is a more dangerous assumption for a model than for a typical service — the retraining/re-evaluation cadence has to be a deliberate, scheduled part of the maintenance plan, not an afterthought triggered only when someone notices quality dropping.

## 8. How to structure and break down an ambiguous operational problem

This is the part that doesn't come from reading a doc — it's a repeatable process. Here's the version worth internalizing, in order, and §9 immediately below works a real incident through every step of it so it's not just an abstract list.

1. **Separate "what is broken" from "what is the impact."** These get conflated constantly under pressure. "The database is in recovery mode" is a symptom; "customers can't get responses from the model registry" is the impact. Chase impact first — it tells you how urgently and how far you need to dig before you've spent time on the symptom.
2. **Look for correlation across unrelated components before assuming independent root causes.** If three services that share nothing in code all fail in the same one-minute window, that's evidence pointing at a shared *substrate* (host, network, VM, disk) — not three coincidental bugs. This is the single highest-leverage pattern-match in ops debugging: unrelated simultaneous failures almost never have independent causes.
3. **Distinguish "this component is broken" from "this component is a victim."** A service reporting an error is not necessarily the thing that's actually wrong — it might just be the first thing to notice a lower-layer problem (a full disk, a network partition, a starved host) and say so loudly. Fixing the loud, visible symptom without checking the layer underneath it is why the same failure comes back five minutes later.
4. **Form a hypothesis, then find the cheapest possible test of it — before committing to an expensive fix.** "I think the disk is full" costs one `df -h` to check. Don't reset, restart, or rebuild anything until the cheap check has actually confirmed or ruled out the hypothesis — expensive actions (especially destructive ones) should follow evidence, not precede it.
5. **When a fix doesn't fully resolve the symptom, ask what the fix's own side effects might have caused — don't assume a second, unrelated bug.** The most common trap in incident response is treating every new error after a fix as a brand-new problem, when it's frequently a direct, explicable consequence of the fix itself.
6. **Once stable, ask "why did this happen" one more level down than the immediate trigger** — the proximate cause (a corrupted VM disk) and the root cause (the host had no free space to begin with) are usually different, and fixing only the proximate cause guarantees a repeat.
7. **Write down what you'd do differently next time, while it's fresh** — not as a postmortem-template exercise, but because the pattern you just pattern-matched (§8.2 above) is exactly the kind of thing you want pre-loaded next time it happens, so you're not re-deriving it from scratch again.

## 9. A real-world ops problem, reasoned through out loud — the Docker Desktop VM-disk-corruption incident

This isn't a hypothetical — it's exactly what happened earlier in this session, worked through in real time, mapped explicitly onto the §8 framework so the framework isn't just an abstract list.

**The starting signal** (§8.1 — separate symptom from impact): the surface-level report was three log dumps that looked unrelated — MLflow's Postgres backend saying "the database system is in recovery mode," a Langfuse worker throwing Redis socket timeouts, and a Grafana log line that turned out to be a complete red herring (an `info`-level feature-flag check, not an error at all — worth noting explicitly: not everything that looks alarming in a log dump *is* alarming; part of triage is recognizing noise). The *impact*, once separated from the symptom, was: the `/chat` endpoint returned a 500, and the model registry API was unreachable. That's the thing that actually mattered to a user — the Postgres log line was a clue toward the cause, not the problem itself.

**The correlation check** (§8.2): Postgres (MLflow's) and a *completely separate* Postgres (Langfuse's own `langfuse-db`) both hit "recovery mode" in the same roughly one-minute window, and Langfuse's Redis-based worker queue timed out in that same window. Three services sharing zero application code, failing simultaneously — that's the pattern-match that says "look at the shared substrate," not "debug three independent bugs." The substrate here is the single Docker Desktop VM every container runs inside.

**Confirming the hypothesis cheaply before acting** (§8.4): rather than immediately restarting anything, the first move was reading Postgres's own log tail directly — which showed `fsync` calls (normally sub-millisecond) taking 10, then 20, then 30+ seconds, climbing in a clear pattern. That's a specific, checkable claim ("the disk subsystem itself is pathologically slow") rather than a guess, and it cost nothing but a log read to confirm.

**The first fix attempt, and reading its outcome honestly** (§8.5): stopping Ollama (the single biggest active CPU consumer at that moment) relieved enough contention that Postgres's own recovery finished on its own within about 30 seconds — confirmed, not assumed, by watching `pg_isready` flip from "rejecting connections" to "accepting connections" in real time. That's the loop closing correctly: hypothesis → cheap confirmation → targeted intervention → observed result, not "restarted something and hoped."

**Where a *second*, structurally different problem showed up** (§8.5 again, the trap of assuming a new bug): re-running the same build a while later hit `write /var/lib/docker/buildkit/metadata_v2.db: read-only file system` — superficially a brand-new error, but the correct move was asking "is this the same substrate problem, further downstream" before treating it as unrelated. It was: the earlier I/O pathology had tipped the VM's filesystem into a protective read-only remount. Confirmed cheaply (`docker run --rm alpine ... mkdir` failing too — the *entire* filesystem was read-only, not just one path), which ruled out "this one build step is broken" and pointed at "the whole VM's disk is broken."

**Escalating past the cheap fixes once they were genuinely exhausted** (§8.4, and knowing when a hypothesis has actually been *disproven*, not just not-yet-confirmed): a full app-level Docker Desktop restart didn't clear it — meaning the corruption lived in the persistent VM disk *file* on the host, not in-memory VM state. That's a different layer of the same problem, and it changed what the next action needed to be (recreate the disk file, not just restart the process reading it).

**The root-cause question, one level past the proximate trigger** (§8.6): recreating the VM disk file *still* hit the same read-only error within minutes on a supposedly-fresh disk. That's the signal that the proximate cause (a corrupted disk file) was itself downstream of something else — checking host disk space directly (`df -h /`) found the real root cause: the host had **~1GB free out of 228GB**. The VM's virtual disk is a sparse file that grows on demand; with the host itself nearly full, *any* fresh VM disk would hit the same wall and get remounted read-only again almost immediately. Recreating the corrupted file without fixing this would have looped forever — this is exactly why §8.6 says go one level past the immediate trigger, not just past the first symptom.

**Freeing real space, and re-discovering the same lesson at a smaller scale**: a large chunk of the "missing" space turned out to be the corrupted VM-disk *backup* that had been kept out of caution during the previous step — 32GB, doing nothing useful, blocking the actual fix. That's the same "don't assume a kept-for-safety artifact is harmless" lesson §8.5 describes, just recursively, one layer inside the incident itself.

**Closing the loop, and what the postmortem note (§8.7) actually is here**: the resolution wasn't "restart Docker" — it was disk space, at the host level, that had been silently draining for a long time (unrelated dev tools, VM images, caches accumulating over months) until a resource-intensive session finally hit the wall. The durable lesson worth carrying forward isn't "Docker Desktop is flaky" — it's "when a VM-level or container-level filesystem starts behaving pathologically, check host disk space *before* assuming application-level corruption," because that check costs one command and would have shortened this whole incident by several steps if it had come first instead of after two other fixes had already been tried.

## 10. CI/CD, automation, and infrastructure design decisions

`02-llmops-mlops-tooling.md` §9 covers the CI/CD *tooling* landscape (GitHub Actions vs. Azure DevOps vs. Jenkins) and `03-reliability-debugging-ops.md` §7 covers where the org stands today. This section is the *decision framework* underneath choosing any of them — the questions that matter more than which specific tool wins.

- **Build vs. buy, evaluated per-component, not once for the whole stack.** A unified LLM gateway, a model registry, an eval harness — each of these has a mature open-source or managed option. The decision isn't "should we build custom tooling" as a blanket policy; it's "does this specific piece have unusual enough requirements to justify not using the well-trodden option," asked separately for each piece. This project deliberately runs real open-source pieces (MLflow, Langfuse, Feast) rather than reinventing them, specifically to demonstrate what "buy" (or rather, self-host the OSS option) looks like in practice versus a hand-rolled equivalent.
- **Where does a quality gate actually belong in the pipeline, and what does it block?** A gate that runs after deploy is a detection mechanism, not a prevention mechanism — useful, but a different guarantee than one that blocks a merge or a promotion. `eval-service`'s scenario-based grading is designed to gate a promotion decision (did the new model/prompt version actually get better, not just different) — deciding whether that gate is advisory (a human reads the score) or blocking (the pipeline refuses to promote below a threshold) is itself a real design decision with a real tradeoff: blocking gates catch more regressions automatically but can also block a genuinely fine change on a noisy metric.
- **Rollback has to be at least as automated as promotion, or it won't be used under pressure.** If promoting a new model is one click/command but rolling back requires archaeology (which was the previous version, where's its artifact, how do I point traffic back at it), rollback won't happen fast enough during an actual incident — which is precisely why [`../../services/mlflow/train_and_log.py`](../../services/mlflow/train_and_log.py)'s walkthrough treats rollback as a first-class, equally-automated step, not an afterthought bolted onto the promotion script.
- **Offline-first is a legitimate infrastructure design decision, not just a workaround.** This project's [`../../scripts/offline-up.sh`](../../scripts/offline-up.sh) exists because container-level network egress genuinely broke on some networks with no software fix available — and the response was to build a real, idempotent, documented fallback path (download on the host, inject via pre-built images) rather than treat it as a one-off manual workaround each time it happened. The design lesson generalizes past this one script: when a dependency (network, a third-party API, a registry) is unreliable in a way you can't fix, building a documented, repeatable path *around* it is infrastructure work worth doing properly, not a hack to feel bad about.
- **Automation should reduce the number of manual steps a human has to get right under pressure, not just reduce total effort in the common case.** A script that saves five minutes on the happy path but requires manual intervention (and judgment about *which* intervention) the moment anything unusual happens has moved the risk, not removed it. This is the same principle behind why `run_training.sh` runs training inside a pinned Python-version container instead of "just `pip install` on whatever's on the host" — it removes an entire category of environment-mismatch failure rather than documenting how to avoid it and trusting everyone to remember.

## 11. Reliability, observability, and scale in production

`03-reliability-debugging-ops.md` covers most of this in depth (latency, debugging, baselines/rollback, SRE practices). This is the compressed, decision-oriented version, with the scale dimension added.

**The four signals worth instrumenting on any AI service, in priority order**: (1) **error rate** — requests that failed outright, the most unambiguous signal; (2) **latency**, at P50 *and* P95/P99 separately — an LLM system's tail latency behaves very differently from its median (one slow provider fallback, one long generation, one retrieval timeout) and averaging them together hides exactly the thing worth alerting on; (3) **quality**, which is AI-specific and easy to skip — eval pass rate, online-eval judge score, groundedness — because a service can have zero errors and fast responses while confidently returning wrong answers, and nothing about error rate or latency would ever surface that; (4) **cost**, per §3 above, because an AI service can degrade financially while looking perfectly healthy on every other signal. This project's Grafana dashboard ([`../../services/observability/grafana/dashboards/aiops-overview.json`](../../services/observability/grafana/dashboards/aiops-overview.json)) is deliberately built around exactly the first three of these (request rate, error rate, P50/P95 latency, eval pass rate, eval avg score) — cost isn't in there today, which is itself worth noticing as a gap given §3's argument that cost deserves the same alerting seriousness as an SLO.

**Observability is the precondition for debugging (`03-reliability-debugging-ops.md` §4), and tracing is the AI-specific piece that logs alone can't give you.** A traditional service's log line usually tells you which code path ran; an agent/RAG system's single user-visible turn can span retrieval, one or more tool calls, a routing decision, and a generation step — a trace showing the *whole chain* in order, with input/output at each step, is what makes debugging tractable instead of guesswork. This is precisely why this project wires Langfuse into all four custom services rather than treating tracing as optional instrumentation — see [`../testing-and-navigation.md`](../testing-and-navigation.md) §3b for exactly how to read one of those traces.

**Scale changes which failure modes matter, and reliability work has to anticipate the shift, not just react to it.** At low volume, an individual slow request or an occasional error is a minor annoyance; at high volume, the same per-request failure rate turns into a steady stream of failed requests large enough to page someone, and a shared bottleneck (a single database connection pool, a rate-limited upstream provider, a single-threaded model server) that never mattered at low traffic becomes the entire system's ceiling. The concrete lever set, roughly in order of how early to reach for each: (1) **horizontal scaling of stateless services** — cheap and simple, works until a shared resource downstream stops scaling with it; (2) **caching** — for AI systems specifically, this includes caching embeddings (don't re-embed identical text) and caching retrieval results for repeated queries, not just the usual HTTP-response caching; (3) **provider fallback chains for availability under load**, not just for outages — [`../../services/llm-gateway`](../../services/llm-gateway)'s multi-provider chain is exactly this, and it's the same mechanism whether the trigger is "the primary provider is down" or "the primary provider is rate-limiting us under this traffic level"; (4) **queueing/backpressure** instead of accepting unbounded concurrent load and letting everything degrade together — better to queue and shed load deliberately than let every in-flight request slow down together until the whole service times out.

## 12. Synthesis: the judgment underneath all of it

If there's one habit that separates "knows the tools" from "can actually run this in production," it's this: **treat every alarming signal as a claim to be checked, not a fact to be reacted to** — and check it at the cheapest layer that could explain it before reaching for an expensive fix. §9's incident is the concrete proof of this in practice: every genuinely wrong turn in that incident (assuming the log-line panic was the whole story, not checking host disk space sooner, nearly leaving a 32GB corrupted backup in place) was a case of reacting one layer too high instead of checking one layer lower first. Every genuinely right turn was the opposite — read the actual log before restarting anything, confirm read-only-ness with a trivial `docker run` before assuming it was scoped to one build, check `df -h` before recreating a VM disk a second time.

None of the individual facts in this file — token costs, alias-based versioning, which database shape fits which access pattern — are hard to learn from a doc. The judgment to reach for the right one, in the right order, under real ambiguity and real time pressure, is only built by doing it — which is the entire reason this project is a runnable stack and not just another doc.
