# LLMOps / MLOps Tooling — Textbook Definitions vs. What a Real Org Actually Runs

_This is a reference doc, not a survey of what any specific company *should* buy. Every "how a real org uses it" section below is drawn from patterns commonly seen across production AI orgs — a mix of conversational-AI, voice-AI, internal tooling, and eval services — not from what a typical AI stack "should" look like in theory. Where a tool commonly isn't used at all, that's stated plainly, along with what it would buy the org if adopted and what (if anything) currently limps along in its place._

---

## 1. LLMOps vs MLOps vs AIOps

**What they are.** These three terms get used interchangeably in vendor marketing, but they sit on different axes. **MLOps** is the classic discipline of taking a model you *train* — collect data, engineer features, run experiments, pick a winner, deploy it, monitor for drift, retrain — and turning that into a repeatable pipeline instead of a one-off notebook. **LLMOps** is MLOps's younger cousin, adapted for a world where you usually don't train anything at all: you call a hosted foundation model over an API, and the thing you version, test, and roll back isn't a model artifact but a *prompt*, a *chain/agent graph*, a *retrieval pipeline*, or a *provider-fallback policy*. The operational concerns rhyme (versioning, testing, monitoring, rollback) but the unit of change is completely different. **AIOps** is a different axis entirely — it's *using* AI/ML to run IT operations (anomaly detection on metrics, log-noise reduction, auto-remediation of infra incidents). It has nothing to do with building AI products; it's about using ML as a tool inside classic ops/SRE work. The confusion is understandable because all three have "Ops" in the name and all three showed up in the same five-year window, but "I do LLMOps" and "I do AIOps" describe two people who might never talk to each other.

**The problem each solves.** MLOps solves "how do I stop losing track of which dataset/features/hyperparameters produced the model currently in production, and how do I safely replace it." LLMOps solves the same governance problem but for a stack where the "model" is a black box you rent by the API call — so the versioning burden shifts entirely onto *your* code: the prompt template, the tool schema, the retrieval query, the fallback order between providers. AIOps solves "my ops dashboards have too much signal for a human to triage by eye — can a model flag the anomaly before a human notices the graph looks weird."

**How this typically plays out.** A production conversational-AI agent is often close to a textbook-perfect LLMOps shape: it trains nothing, and everything that would be "model versioning" in an MLOps world instead shows up as prompt/chain code, provider-selection logic, and fallback ordering across OpenAI/Anthropic/Gemini — all of it living in application code and Git history rather than a model registry. A dead, ad-hoc fine-tuning script somewhere in the org (one that produced a checkpoint referenced by ID in a code comment, never registered anywhere) is often the *only* place that actually touched classic MLOps-style model training — and notably, it tends to die without ever growing the tracking/registry infrastructure real MLOps would demand. It's also common for nothing in the org to do AIOps yet: no anomaly detection running against infra or ops metrics anywhere. An internal code-review bot backed by a local LLM looks superficially AIOps-adjacent because it's "AI applied to an engineering process," but it's reviewing pull requests, not watching infra metrics for anomalies — that's AI-for-engineering-productivity, not AIOps in the anomaly-detection-on-infra sense.

**First thing to wire up if adopting AIOps tomorrow.** Don't start with a fancy anomaly-detection platform — start with feeding your existing log volume/error-rate time series (already collected from nearly every service, see section 10) into a basic seasonal anomaly detector (even a cloud provider's built-in anomaly detection on a couple of key service metrics) so a spike gets flagged before someone notices it manually. That's a narrow, low-risk slice of AIOps an org could stand up without touching any AI product code.

## 2. LangChain vs LangGraph

**What they are.** LangChain is a library for composing LLM calls into chains and agents: prompt templates, output parsers, tool-calling wrappers, memory/history persistence, and (in its "classic" agent API) a `create_tool_calling_agent` + `AgentExecutor` loop that lets a model decide which tool to call next, up to some iteration cap. LangGraph is a separate, newer library built by the same team specifically for cases where a plain loop isn't expressive enough: you need a graph of nodes and edges with explicit state, the ability to cycle back to earlier nodes, conditional branching between multiple specialized agents, human-in-the-loop interrupts that pause execution and resume later, and durable checkpointing of that state so a long-running multi-agent process can survive a restart.

**The problem each solves.** Classic LangChain agents solve "let a single model call tools in a loop until it decides it's done" — simple, and sufficient for a large fraction of real agent use cases. LangGraph solves the harder problem that shows up once you have *multiple* agents that need to hand work off to each other: without an explicit state machine, you end up hand-rolling your own control flow to decide when Agent A should defer to Agent B, how to prevent them from bouncing the conversation back and forth forever, and how to persist that hand-off state if the process needs to pause or restart. That control-flow logic is exactly the kind of thing that's easy to get almost-right and hard to get fully right by hand.

**How this typically plays out.** LangChain often ends up used throughout a production conversational-AI system — the classic agent stack (`create_tool_calling_agent` + `AgentExecutor`, some iteration cap like 10), a persistence layer's `RunnableWithMessageHistory` for conversation history, `langchain-mcp-adapters` for loading MCP tools, and provider integrations wrapped in `.with_fallbacks()` for cross-provider failover. LangGraph, by contrast, is often confirmed absent everywhere in an org that hasn't adopted it yet. That matters concretely because a hand-rolled coordinator will often implement multi-agent hand-off logic *by hand*, on top of the classic `AgentExecutor` loop — including manual "anti-ping-pong loop protection" code whose entire job is stopping two agents from endlessly handing a conversation back and forth. That's precisely the failure mode LangGraph's explicit graph model exists to prevent structurally (a well-formed graph can't cycle indefinitely between two nodes unless you explicitly wire an edge that allows it), rather than needing a bespoke guard clause discovered after the fact.

**Cost of the gap.** The hand-rolled coordinator works, but it's bespoke code that has to be understood, tested, and maintained by whoever touches it, with no reusable abstraction for the next multi-agent feature — every new hand-off pattern likely needs its own guard logic rather than reusing a graph primitive.

**First thing to wire up if adopting LangGraph tomorrow.** Don't do a big-bang rewrite of the existing coordinator. Pick the single existing hand-off path with the anti-ping-pong guard, model it as a 3-4 node LangGraph graph (coordinator → sub-agent A → sub-agent B → back to coordinator, with an explicit max-cycle edge condition instead of a manual counter), and run it side-by-side with the existing implementation on a shadow-traffic slice before touching production routing.

## 3. LangSmith vs Langfuse vs raw OpenTelemetry

**What they are.** All three answer the same question — "what actually happened inside this LLM call/chain, and was the output any good?" — with different tradeoffs. **LangSmith** is LangChain's own SaaS tracing and evaluation product: point env vars at it, and every LangChain run gets automatically traced, with a UI for inspecting spans, attaching feedback, and running dataset-based evaluation experiments. **Langfuse** is an open-source LLM observability platform you can either use as SaaS or self-host; it's framework-agnostic (works whether or not you use LangChain) and adds first-class support for scoring/tagging traces after the fact, which makes it a natural fit for logging *evaluation* results (not just raw traces) against production runs. **Raw OpenTelemetry** is the vendor-neutral instrumentation standard used across all of software observability, not just LLM apps — you emit spans/metrics through the OTel SDK and export them to whatever backend you want (Jaeger, Honeycomb, Datadog, Prometheus), which means zero lock-in but zero LLM-specific tooling out of the box (you build your own conventions for what counts as a "trace" for an LLM call).

**The problem each solves.** Without one of these, debugging why an agent gave a bad answer means grepping through unstructured logs trying to reconstruct which prompt, which retrieved documents, and which tool calls led to the output — painful even once, unworkable at scale. LangSmith solves it with the least setup cost if you're already all-in on LangChain. Langfuse solves it with more operational ownership (you run the infrastructure) in exchange for keeping trace data in-house and getting a system built around scoring pipelines. Raw OTel solves it with maximum flexibility and reuse of infra your team may already run for non-LLM services, at the cost of building your own LLM-specific span conventions from scratch.

**How this typically plays out — a genuine three-way split.** It's common for a text-based conversational agent to use LangSmith, with `run_id` deliberately set to the same `trace_id` returned to API clients so a user-facing feedback event can be correlated back to the exact trace that produced it. A self-hosted Langfuse deployment (web, worker, Postgres, ClickHouse, Redis, S3-for-media, behind a load balancer, public at an internal subdomain) might instead be consumed by a voice-AI backend (per-turn voice latency scoring: STT time, LLM first-token time, TTS first-audio time, end-to-end, with P95 tracking) and by an eval service (every evaluator run wrapped in a Langfuse span, with `langfuse_trace_id`/`langfuse_observation_id` persisted on result documents). A third service — a data-engineering team's internal bot, say — might use neither, running its own Prometheus client plus OpenTelemetry SDK instead, with spans for tool/request events and OTLP export to Jaeger/Honeycomb/Datadog if configured.

**The real cost of not unifying.** A voice-latency regression in one product and a chat-hallucination bug in another can live in two entirely separate dashboards, owned by different tooling, with no shared trace ID space — nobody can pull up one timeline and see that a slow LLM response in the voice pipeline correlates with a provider fallback event that also affected chat quality that day, because LangSmith and Langfuse don't talk to each other. Three observability stacks across a dozen-plus repos also means three sets of on-call runbooks, three places to check when something's wrong, and no single person who can debug the whole AI surface without learning three tools.

**First thing to wire up tomorrow.** Not a migration — that's a multi-quarter project with real switching costs on both the LangSmith and Langfuse sides. The cheap win is cross-linking: have the LangSmith-based service also emit its `trace_id` as a tag/metadata field on any Langfuse-side artifact that references the same conversation (e.g., if evals ever score that service's transcript), so at least a human debugging an incident that spans both products can pivot from one dashboard to the other by ID, even without full platform consolidation.

## 4. Langflow and other low-code/visual agent builders

**What they are.** Tools like Langflow (and similarly, Flowise, or LangChain's own newer visual builders) let you construct an LLM pipeline — prompt → retrieval → tool call → output — by dragging and connecting nodes in a browser UI instead of writing code. The generated pipeline is usually still backed by a real framework (Langflow, for instance, is built on LangChain under the hood) so it can be exported or run programmatically, but the primary interaction model is visual composition.

**The problem it solves.** Two real problems: fast prototyping (a developer can sketch a RAG pipeline and see it run in minutes without setting up a project scaffold), and accessibility for people who aren't comfortable writing Python/JS but understand the conceptual shape of a pipeline — a product manager or solutions engineer can wire together a demo agent without waiting on an engineer. For simple, mostly-linear pipelines with a handful of well-known node types, this genuinely removes friction.

**How this typically plays out.** A lot of orgs use no low-code or visual agent-building tool at all — every agent and pipeline is hand-coded, from a multi-provider conversational agent to a voice pipeline to an internal NL-to-SQL agent. This isn't a gap so much as a reflection of what the org's needs actually look like.

**Why a codebase like this would likely outgrow a visual builder fast, if it tried one.** The moment you look at what a production conversational agent actually does — automatic `.with_fallbacks()` cross-provider failover chosen per-call across OpenAI/Anthropic/Gemini, MCP tool loading, database-backed conversation history with custom session keys, per-tenant auth headers threaded through every call — none of that maps cleanly onto a drag-and-drop node graph. Visual builders are good at expressing "prompt → retrieve → generate" style pipelines; they're not good at expressing "if provider A returns a rate-limit error, retry on provider B with a re-mapped tool schema, but only if this tenant's config allows Gemini." That kind of business logic either has to be smuggled into a custom node (at which point you're writing code anyway, just inside an unfamiliar plugin API) or it doesn't fit the tool at all. An org's actual AI surface is often closer to "several bespoke backend services with deep per-tenant configuration" than "a small number of demo-able pipelines," which is exactly the profile that outgrows visual builders within weeks rather than benefiting from them long-term.

**First thing to try if adopting one tomorrow.** If there's ever a genuine need (e.g., letting a non-engineer sketch a first draft of a new agent's tool-calling flow before an engineer hardens it), scope it strictly to throwaway prototyping — never point a visual builder's output at production config or let it become the source of truth for a shipped pipeline. Use it as a whiteboard, export the design, then hand-implement it the way every other agent in the org is implemented.

## 5. MLflow

**What it is.** MLflow is an open-source platform for the parts of MLOps that get unmanageable fast without tooling: **experiment tracking** (log every training run's parameters, metrics, and artifacts so you can compare them later), and the **model registry** (a versioned catalog of trained model artifacts, where each version can be tagged with a lifecycle stage or alias — e.g., `champion`, `staging`, `production` — and promoted or demoted without touching application code).

**The problem it solves.** Without it, "which model is actually running in production, and what data/code produced it" becomes tribal knowledge — a Slack message, a comment in a script, a filename convention that inevitably drifts. MLflow solves this by making model lineage a queryable record: version 17 was trained from dataset snapshot X with these hyperparameters, scored Y on the eval set, and is currently aliased `production`.

**What "baseline" and "rollback" concretely mean in MLflow terms**, since this is the part worth being precise about: you **register** a trained model as a new version in the registry (`mlflow.register_model(...)`, giving you e.g. version 12). You **set a baseline** by assigning an alias to a version — e.g., pointing the `champion` alias at version 10 means "this is the version everything is compared against." Serving code doesn't reference a version number directly; it resolves the alias (`models:/my-model@production`) at load time. To **promote** a new candidate, you evaluate version 12 against the `champion` baseline, and if it wins, you re-point the `production` alias to version 12 — no code deploy, no redeploying serving infra, just a metadata update in the registry. To **roll back**, you do the exact same operation in reverse: re-point `production` back to version 10. The old version was never deleted, so reverting is a metadata change, not a re-training or re-deployment event — this is the entire value proposition over "the model is just a file our deploy script copies somewhere."

**How this typically plays out: it often just isn't used yet.** MLflow (or any other experiment-tracking/model-registry/model-versioning tool) is a common gap in orgs whose AI investment is mostly LLM-based rather than classic ML. The closest thing that tends to exist instead is a dead ad-hoc fine-tuning script, which produced a checkpoint and referenced the resulting model ID directly in a code comment. There's usually no tracked lineage from the dataset that produced that model, to the training run, to that model ID — if someone needed to know what data trained it, or wanted to "roll back" to a prior fine-tune, there's nothing to roll back *to*, because no prior version was ever registered. This is the sharpest example of the gap MLflow exists to close: the fine-tuning happened once, worked well enough to ship, and then all its provenance evaporated into a comment.

**First thing to wire up tomorrow.** If an org ever revives fine-tuning like this, the very first step — before any new fine-tuning run — is standing up an MLflow tracking server (even the simplest self-hosted SQLite+local-artifact-store config) and registering that one model retroactively: log the dataset reference and hyperparameters that produced it as version 1, alias it `production`, and require every future fine-tune to go through the same registration step before its model ID is allowed to appear in application code.

## 6. Kubeflow

**What it is.** Kubeflow is a collection of Kubernetes-native tools for running ML workloads — pipeline orchestration (multi-step training/eval DAGs as Kubernetes-native objects), distributed training operators, hyperparameter tuning (Katib), and model serving (KServe) — all built on the assumption that you already have a Kubernetes cluster and want your ML workflows to be first-class citizens of it, scheduled and scaled the same way the rest of your k8s workloads are.

**The problem it solves.** For an org already running Kubernetes, Kubeflow solves "we don't want ML pipelines to be a separate, bespoke set of cron jobs and scripts outside our normal infra story — we want training and serving to use the same scheduler, the same RBAC, the same observability hooks as everything else." It's valuable specifically because it *doesn't* introduce a new infrastructure paradigm; it extends the one you already have.

**Why it often doesn't fit an org running plain ECS/EC2, concretely.** Kubeflow is Kubernetes-native, full stop — there is no meaningful way to run it without a Kubernetes cluster underneath it. An org that runs everything on plain container orchestration (ECS, say) with zero Kubernetes clusters anywhere would find that adopting Kubeflow isn't "install a new tool" — it's "stand up and operate an entirely new orchestration platform (EKS or self-managed k8s) that the org has no current operational experience with, migrate some non-trivial slice of workloads onto it to justify the cluster's existence, and now maintain two container orchestration systems side by side, or undertake a much larger migration off the existing platform entirely." That's a platform decision with organization-wide blast radius, not an incremental tooling pick — and it would need to be justified by training/serving workloads that the existing platform genuinely can't handle, which a lot of LLM-centric orgs don't currently have (nothing trains models at any meaningful scale; inference is entirely hosted-API or a single self-hosted local-model instance).

**First thing to check before even considering it.** Don't evaluate Kubeflow features — evaluate whether there's a training workload on the horizon large/frequent enough to justify running Kubernetes at all, independent of Kubeflow. If that workload doesn't exist yet, the prerequisite question ("should we run Kubernetes anywhere in this org") has to be answered first, and it's a much bigger conversation than ML tooling.

## 7. Amazon SageMaker and Amazon Bedrock

**What they are.** These are AWS's two distinct answers to "how do you run AI workloads without building your own infra," and it's worth being precise about the difference because they solve different problems. **SageMaker** is for when you're training your own models or fine-tuning existing ones and need to host and manage them — notebooks, training jobs, hyperparameter tuning, and managed endpoints for models you own the weights of. **Bedrock** is for when you're *not* training anything and just want unified, hosted API access to a menu of foundation models (Anthropic, Meta, Amazon's own models, and others) from multiple vendors behind one consistent API, one IAM/billing surface, and one place to configure guardrails — it's AWS's answer to "give me one API instead of five vendor SDKs."

**The problem each solves.** SageMaker solves the classic MLOps infra problem — training and serving your own models without hand-rolling GPU provisioning, checkpointing, and endpoint scaling. Bedrock solves a narrower but very live problem for LLM-consumer orgs: without it, every service that wants to call multiple LLM providers reimplements its own abstraction layer for "pick a provider, format the request, handle provider-specific errors, fail over to another provider" — and if you're already deep in the AWS ecosystem, Bedrock gives you that abstraction as a managed service with a single IAM policy surface instead of juggling separate API keys/SDKs per vendor.

**How this typically plays out: neither is used.** It's common for all model inference in an LLM-centric org to go through hosted vendor APIs directly (`openai`, `anthropic`, `google-generativeai` SDKs) or a self-hosted local-model instance for internal tooling — nothing trained or served via SageMaker. And instead of Bedrock's unified API, each service that needs multi-provider access ends up building its *own* abstraction: a chat product with `get_llm()` + `.with_fallbacks()` doing cross-provider failover, and a voice product using `litellm` for the same conceptual job. That's two separately-maintained provider-abstraction layers solving the same problem differently, in a codebase with zero SageMaker or Bedrock footprint.

**Why Bedrock specifically is worth naming as a candidate.** If an org like this adopted Bedrock, it could plausibly collapse both of those hand-rolled layers into one AWS-native abstraction with a single IAM policy, one place to see spend across both products, and one guardrails/logging configuration instead of two. That's a real consolidation win, not a hypothetical one, when the org already runs everything else on AWS.

**The real tradeoff, stated honestly.** Bedrock's model menu is a subset of what direct vendor APIs offer — not every OpenAI or Google model shows up on Bedrock the same day it launches elsewhere, and Bedrock adds AWS as an intermediary between the org and every model call, meaning outages or throttling on Bedrock's side become a shared failure point across every product using it. Consolidating onto Bedrock trades "two independently-maintained fallback implementations, each free to adopt any provider's newest model immediately" for "one consistent layer, one bill, one IAM surface — but bounded by whatever AWS has onboarded to Bedrock and whatever throttle limits Bedrock itself imposes." That's a legitimate architectural bet, not a strictly-better move.

**First thing to wire up tomorrow.** Don't attempt a full cutover. Pick one non-critical fallback path in the voice product's `litellm` config (which already treats providers as swappable) and add Bedrock as one more backend behind `litellm` — `litellm` already supports Bedrock as a provider target, so this is a config change, not a rewrite — and compare latency/cost/reliability against the existing direct-API providers before considering it for the chat product's more deeply embedded fallback logic.

## 8. AI infrastructure and unified LLM gateways

**What this is.** A unified LLM gateway (litellm, Bedrock, OpenRouter, Portkey, and similar tools) is the pattern of putting one internal API in front of every LLM provider your org calls, so individual services stop reimplementing provider selection, retries, rate-limiting, cost tracking, and fallback logic each on their own. Instead of every team writing its own `try OpenAI, catch rate-limit, fall back to Anthropic` logic, they call one gateway with a consistent request shape, and the gateway owns the provider-specific plumbing, plus (in the fuller versions of this pattern) centralized cost attribution per team/service and consistent rate-limit enforcement across the whole org rather than per-service quotas that don't know about each other.

**The problem it solves.** Without a gateway, provider abstraction logic gets duplicated N times across N services, each with its own bugs, its own idea of what counts as a retryable error, and no shared visibility into total spend or rate-limit headroom across the org — if one service is quietly burning through a shared API key's rate limit, another service calling the same provider has no way to know. A gateway centralizes that so there's one place to add a new provider, one place to see aggregate cost, and one place to enforce a global rate-limit policy instead of hoping every service's local retry logic behaves.

**How this typically plays out.** It's common for an org to have one real, if partial, instance of this pattern: a voice product using `litellm` for multi-provider LLM access — one of the very few places in the org using an actual unified-gateway library rather than hand-rolling one, notable precisely because it's the exception. A chat product, meanwhile, might solve the identical conceptual problem (call multiple providers, fail over between them) with its own hand-built `get_llm()` + `.with_fallbacks()` logic — a separate, parallel implementation of the same idea, maintained independently, with no shared cost tracking or rate-limit coordination between the two. So the org doesn't lack the *pattern* — it has two products independently reaching the same conclusion that they need provider abstraction — it lacks the *consolidation*: there's no single internal gateway that both products call through, which means a provider outage or rate-limit event affecting OpenAI, say, has to be diagnosed and mitigated twice, once per product, with no shared dashboard showing combined spend or combined rate-limit consumption against that provider. (This project's own `llm-gateway` is exactly the consolidated version of this pattern — see the root README.)

**First thing to wire up tomorrow.** Don't try to merge two independent fallback implementations into one shared internal service in one shot — that's a real migration with two different call-sites' worth of edge cases. Start by putting `litellm`'s proxy mode (a lightweight OpenAI-compatible HTTP gateway that `litellm` ships out of the box) in front of the voice product's existing usage first, since that's already using `litellm` as a library — this gets one real service to expose provider-agnostic cost/latency metrics per call *before* asking the chat product to give up its bespoke `.with_fallbacks()` logic for the same gateway. Prove the gateway pattern works operationally on the service that's already closest to it, then make the case for the other product to migrate onto the same gateway next.

## 9. CI/CD landscape — GitHub Actions vs Azure DevOps vs Jenkins

**What they are, at a level relevant here.** Jenkins is the classic self-hosted CI/CD server, built around pipelines-as-code (Jenkinsfiles) and shared libraries for reusing pipeline logic across many repos. GitHub Actions is GitHub's own CI/CD, defined as YAML workflows living in `.github/workflows/`, with a large marketplace of reusable actions and no separate server to operate since it's SaaS. Azure DevOps is Microsoft's equivalent suite (Pipelines, Repos, Boards) — commonly the default choice for orgs already standardized on Azure/Microsoft tooling. None of these is inherently "for AI" — they're general CI/CD systems — but which one an org standardizes on shapes how easy it is to add AI-specific pipeline steps (model eval gates, prompt regression tests, etc.) later.

**The problem a mature CI/CD setup solves regardless of vendor.** Manually building images, tagging them, pushing to a registry, and updating a running service is slow and error-prone at any real scale — a good pipeline makes "merge to branch X" reliably produce "the right image is built, registered, and deployed to the right environment" with no human running commands by hand, and makes environment promotion (dev → staging → prod) a matter of branch/tag conventions rather than tribal knowledge about who's allowed to deploy what, when.

**How a mature Jenkins setup typically demonstrates this.** It's common for Jenkins to be the org standard, driven by a shared internal library (with variants for different service shapes) that gives every onboarded repo the same pipeline shape: build and tag a Docker image → create the registry repo if it doesn't exist → registry login → push the image → register a deploy task → deploy (a CloudFormation stack update for application services, or a raw `terraform apply` behind a manual-approval gate for infra) → set up autoscaling for prod. Environment progression is entirely branch/tag driven: work on `integration`/`qa` branches, cut an `rc-*` tag to promote to staging, cut a `v*` tag to promote to prod — and prod deploys often require a manual input choosing the target region. This is a mature, classic CI/CD setup — consistent, reusable across repos via the shared library, environment-gated — but it's *not* GitOps: the pipeline imperatively drives deployment (Jenkins calls CloudFormation/Terraform directly) rather than a controller reconciling a Git-declared desired state.

**Why the newest, most prototype-stage services often choose GitHub Actions instead.** A young AI service will often run GitHub Actions instead of onboarding onto the Jenkins shared library — its pipeline running Postgres and Redis as GitHub Actions service containers, then lint, type-checking, unit tests with a coverage gate, and then integration tests — a genuinely more code-quality-focused pipeline than the deploy-focused Jenkins flow. The likely reason is lower ceremony: onboarding a new repo onto the Jenkins shared library means understanding its conventions and getting the right library variant wired up, while a GitHub Actions YAML file can be written and iterated on directly in the repo by whoever's building the prototype, with no shared infrastructure to coordinate with. For a young, fast-moving service that might not survive to production shape, that's a reasonable tradeoff — though it does mean the org now has two CI/CD systems to maintain expertise in, and no shared library reuse between the GitHub Actions pipelines and the Jenkins ones.

**First thing worth doing if this bothers you operationally.** Not a full consolidation — that's disruptive for no clear win given both pipelines currently work. The concrete first step is deciding *now*, before a third prototype service shows up, what the graduation criterion is for moving a GitHub-Actions-based prototype onto the Jenkins shared library once it stops being a prototype, so the two-system split doesn't quietly become three or four.

## 10. Monitoring and observability stack choices

**What the landscape looks like.** This space splits roughly into: logging SaaS platforms (Better Stack/Logtail, Papertrail) that centralize structured logs with search and alerting but generally don't do metrics/tracing; full observability suites (Datadog, New Relic) that bundle logs+metrics+traces+APM in one paid platform; cloud-native metrics (CloudWatch, Azure Monitor) that come free-ish with your cloud provider but are usually clunkier for cross-service correlation; the open-source metrics+tracing combo (Prometheus for metrics, Grafana for dashboards, often paired with Jaeger/Tempo for tracing) that requires you to run and maintain the infrastructure yourself but gives full control and no per-seat licensing; and ELK/OpenSearch for log aggregation and search at a scale logging SaaS pricing makes uneconomical. The meaningful axis isn't "which is best" — it's logs vs. metrics vs. traces (three different signal types that answer different questions) and SaaS-convenience vs. self-hosted-control.

**The problem this category solves.** Structured logs answer "what happened, in what order, for this one request" — invaluable for post-hoc debugging but poor at answering "how is P95 latency trending this week" without expensive log aggregation queries standing in for what a real metrics system gives you natively. Metrics (counters, histograms, gauges scraped or pushed over time) answer the trend/percentile/alerting questions logs are bad at. Traces answer "where did the time go across this request's hops through multiple services," which neither logs nor metrics alone can reconstruct cleanly.

**How this typically plays out.** A logging SaaS platform (Better Stack/Logtail-style) is a common de facto standard across nearly every service in an org — structured JSON logs with request-ID correlation, consistently adopted via a shared logging library. That's a real, org-wide win for the "what happened for this one request" question. But it's also common for no Prometheus, Grafana, Datadog, or cloud-native APM to be wired into any application code anywhere, with maybe one exception: an internal data-engineering bot running its own Prometheus client plus the OpenTelemetry SDK, exporting spans for tool/request events to Jaeger/Honeycomb/Datadog when configured. That can make it the only service in the org with real metrics-and-tracing observability beyond logs and the separate LLM-tracing SaaS tools (LangSmith/Langfuse) covered in section 3. Every other service — including latency-sensitive, customer-facing AI products — often has logs and LLM-specific tracing, but no general-purpose metrics/tracing layer of the kind that one service built for itself.

**What this costs the org concretely.** Answering "what's our P95 API latency this week, broken down by endpoint" for a chat or voice product often means either querying LangSmith/Langfuse (which only see the LLM-call portion of a request, not the whole HTTP request lifecycle) or grepping the logging platform and computing percentiles after the fact from log timestamps — workable but slow, manual, and not dashboard-able the way a Prometheus histogram + Grafana panel would be. There's often no alerting on infra-level latency/error-rate thresholds outside whatever the logging platform's log-based alerting can approximate, and no standard dashboard a new on-call engineer can pull up to see "is the system healthy right now" across the AI product surface — they'd need to check the logging platform, then LangSmith or Langfuse depending on which product, and there's still no view of general request/infra health underneath the LLM-specific layer.

**First thing to wire up tomorrow.** Take whatever OpenTelemetry instrumentation already exists as the template — it's the one proof-of-concept the org already has — and add the same lightweight OTel SDK + Prometheus client pattern to the most latency-sensitive service first, since it likely already computes per-turn latency numbers (STT/LLM-first-token/TTS-first-audio/E2E, for a voice product) that currently only live inside Langfuse spans. Exporting those same measurements as Prometheus histograms alongside the existing Langfuse spans would produce the org's first real Grafana-style P95 latency dashboard outside of a per-vendor LLM-tracing tool, without requiring a decision yet about whether to roll this out everywhere.

## Try it yourself

Reading definitions only gets you so far with tooling like this — this project stands up local, runnable equivalents of three of the tools discussed above so you can exercise these concepts directly instead of taking them on faith:

- A **self-hosted Langfuse** instance, mirroring the same self-hosted-on-your-own-infra pattern a lot of orgs actually run in production for a voice product and an eval service — so you can see real traces and spans land in the same kind of dashboard a voice pipeline might use.
- A local **MLflow** tracking server and model registry — the piece a lot of orgs have zero of anywhere in their stack — so you can actually register a model version, assign it an alias, promote a new version, and practice the "rollback is just re-pointing an alias" move described in section 5, on a toy model rather than a hypothetical.
- A minimal **unified LLM gateway**, mirroring the role `litellm` plays for a voice product in a lot of real setups, so you can see firsthand what centralizing provider selection, fallback, and cost/latency tracking behind one interface buys you over a hand-rolled `.with_fallbacks()` approach.
