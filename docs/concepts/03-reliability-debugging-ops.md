# Reliability, Debugging, and Ops for AI/LLM Systems

_This document assumes you're comfortable with general DevOps/SRE work — Jenkins pipelines, deploy gates, incident response, monitoring dashboards — and focuses on what changes when the thing you're operating is an LLM/agent pipeline instead of a deterministic service. Every "how a real production AI system handles this" note below is drawn from patterns commonly seen across production conversational-AI, voice-AI, and LLM-eval systems — not from what a typical AI stack "should" look like in theory; where a pattern doesn't yet exist in a given system, that's stated plainly as a gap, not a criticism — most orgs running LLMs in production are at a similar stage._

## 1. How to Measure and Compare LLM/Agent Performance

For a normal service, "performance" mostly means latency and error rate. For an LLM/agent system you need four categories, and skipping any one of them means you can ship a "faster" change that's actually worse:

**Latency** isn't one number — it's a pipeline of numbers, and where time goes matters more than the total. For a voice agent, the useful breakdown is per-turn: STT latency (audio in → transcript out), LLM time-to-first-token or TTFT (transcript in → first generated token), TTS first-audio latency (first token → first audible sample), and end-to-end latency (user stops talking → user hears a response start). You track all four with percentiles — P50 tells you the typical experience, P95/P99 tell you what your worst-treated users experience, and for a real-time voice product P95 is usually the number that determines whether the call "feels laggy." Median-only latency dashboards hide exactly the tail behavior that makes a phone call feel broken.

**Cost** should be tracked per unit of value delivered, not per API call — cost per conversation, cost per resolved ticket, cost per completed voice call. A model swap that's 30% cheaper per token but takes 40% more tool-calling round-trips to reach an answer can easily be more expensive per conversation. You can't see that from a per-call cost dashboard alone.

**Quality** for an LLM system is a score, not a pass/fail. The two that matter most: eval pass-rate against a fixed test set (what fraction of test cases meet your success criteria) and groundedness/faithfulness score (what fraction of generated claims are actually supported by retrieved context, for RAG systems). Quality has to be measured continuously against changes, because unlike a compiler, an LLM can silently get worse at a task while staying perfectly "up."

**Throughput** for conversational AI means concurrent sessions the infrastructure can sustain, not requests-per-second — a single voice call holds resources (STT/LLM/TTS state, a WebRTC media stream) for its entire duration, so the right question is "how many simultaneous calls can one box handle," not "how many calls per second."

### A concrete example: measuring a scaling change before shipping it

A production voice-AI backend is a good illustration of instrumentation matching this model — it tracks per-turn STT latency, LLM TTFT, TTS first-audio latency, and end-to-end latency, with P95 tracking, exported to a self-hosted Langfuse instance. That instrumentation is what lets a team *quantify* a real bottleneck instead of guessing at one: a legacy architecture that duplicates VAD/STT/LLM/TTS resources per call, at roughly 40-80MB of memory per call, caps a single 8GB box at around 20 concurrent calls. A documented redesign — a shared-provider-pool architecture where STT/LLM/TTS provider connections are pooled instead of duplicated per call — can target 200+ concurrent calls on the same 8GB box (a 75-87% memory reduction) for an estimated ~20ms of added latency per turn.

That's the model worth copying: don't just say "the new architecture should be faster/cheaper," put a number on the current state (20 calls/box, current P95 latency), a number on the target state (200+ calls/box, +20ms), and use the same instrumentation to confirm the trade actually landed after shipping. Work like this — documented in an internal scaling-strategy write-up and a couple of related design docs — is often the most mature piece of AI ops thinking a team has produced, but it's frequently still a plan rather than confirmed running code.

No other kind of service tends to have comparable latency instrumentation — not a conversational-AI backend, not an eval service, not an internal Slack bot. If you're operating any of those, you often have no way to answer "did that change make things faster or slower" with a number.

## 2. What to Do About Latency

In an LLM/voice pipeline, latency hides in more places than a typical service, and each place needs a different fix.

**Network and queueing** — the mundane stuff — still applies: connection setup to the model provider, DNS, load balancer hops, and any request queue if you're rate-limited or the box is saturated. Standard mitigations (keep-alives, connection pooling, autoscaling on queue depth) still work here exactly as they do for any service.

**Model inference itself** is the part unique to LLMs. A large model call is genuinely slow — hundreds of milliseconds to seconds before the first token, more before the full response. You mostly can't make inference itself faster without changing the model (see the quantization section below), but you can hide the wait: **stream tokens as they're generated** rather than waiting for the full response. For a voice agent, this is not optional — TTS should start synthesizing audio from the first sentence of the LLM's output rather than waiting for the whole reply, or your end-to-end latency becomes the sum of full-LLM-generation-time plus full-TTS-time instead of overlapping them.

**Tool-calling round-trips** are an easy-to-miss latency sink. Every time an agent calls a tool (a KB search, a CRM lookup, an MCP call) and then has to send the result back to the model for another inference pass, you've paid for network latency plus another full model call. A multi-step agentic flow with three tool calls can spend more time in tool round-trips than in actual generation. The fix is architectural: batch tool calls when the model supports parallel tool-use, cache tool results that don't change turn-to-turn, and be deliberate about how many hops a single user turn requires.

**Prompt caching** is one of the highest-leverage latency and cost wins available, and it requires designing for it deliberately — you don't get it by accident. Providers cache the prefix of a prompt (system prompt, tool definitions, retrieved context if it's stable) and skip re-processing it on the next call if the prefix is identical. That means prompt *structure* matters: put the stable, reusable parts (system instructions, tool schemas) first and the turn-specific, changing parts (the user's latest message) last, so the cacheable prefix stays a cache hit across turns. An internal data-engineering team's Slack bot is a concrete example of a system built this way on purpose — its retrieval design is structured specifically to keep the prompt prefix stable across a session so repeated calls hit the provider's prompt cache instead of re-processing the same context tokens every turn. That's a deliberate architectural choice, not a side effect, and it's the pattern to replicate anywhere a new agentic system with static context gets built — copy that structure rather than reinventing it under latency pressure later.

**Provider fallback and timeouts** matter because a hung upstream call (an LLM provider having a bad minute) is worse than an error — it's a stuck request holding resources with no signal that anything is wrong. Set aggressive timeouts on model calls specifically, with a fallback path (secondary provider, cached/canned response, graceful degradation) rather than an unbounded wait. A production conversational-AI system's multi-LLM setup (OpenAI/Anthropic/Gemini with fallback) is the shape of the right idea — the timeout/fallback machinery around a model call is what turns "model provider had a bad minute" from a customer-visible outage into a non-event.

**Connection pooling and pre-warming** is the other half of a production voice-AI backend's proposed redesign: instead of each call spinning up its own STT/LLM/TTS provider connections from scratch (the ~40-80MB-per-call cost), a shared pool keeps warm connections ready and hands them out per call. This is standard connection-pooling practice applied to model-provider connections instead of database connections — the win is avoiding repeated cold-start/handshake cost on every single call.

## 3. What to Do About Hallucinations

"Hallucination" here means the model stating something as fact that isn't supported by its source material — invented CRM data, a fabricated policy, a wrong answer presented confidently. There are four real strategies for dealing with it, in increasing order of how much they cost to run:

1. **Groundedness/faithfulness scoring** — an LLM-judge (or a smaller classifier) checks whether each claim in the answer is actually supported by the retrieved context. This is the most direct hallucination check for RAG systems specifically, because it's checking the exact failure mode (answer not backed by source) rather than a proxy for it.
2. **Retrieval-relevance checks** — before the generation step even runs, check whether the retrieved context is actually relevant to the question. If retrieval failed silently (wrong documents came back), the model is being set up to hallucinate regardless of how good the generation step is — catching this earlier is cheaper than catching it after generation.
3. **Output guardrails** — generic scanners that check the final output against policy (no PII leakage, no disallowed claims, no toxic content). These catch a different category of problem than hallucination — they check *safety/policy*, not *factual grounding*. A response can pass every guardrail check and still be confidently wrong about a fact.
4. **Human-in-the-loop review** — a person spot-checks or reviews flagged conversations. This scales the worst but catches things automated checks miss, and is usually reserved for high-stakes categories or as a feedback loop into eval sets.

### Where a typical org actually stands: eval-time only, not live

This is the most important gap to internalize: **a production org can have good hallucination-detection tooling, but it only runs offline, never on live traffic.** Specifically:

- An eval-tooling service can have a "groundedness" grader — an LLM-judge that scores whether an answer is supported by retrieved context. This is exactly strategy #1 above, and it's well-built. It runs against a dataset, offline.
- An eval service can have `SuccessCriteriaEvaluator`- and `KbAdherenceEvaluator`-style LLM-judges that similarly catch fabrication — again, only in offline eval runs, triggered manually or on a schedule, never against a real customer's live conversation.
- A production conversational-AI backend can have a generic LLM-output scanner and a moderation API wired into the live request path. But — and this is the distinction worth being precise about — those are strategy #3, policy/safety filters. Neither one checks whether a RAG answer is actually grounded in the retrieved context. A response can sail through both live guardrails while still confidently stating something the retrieved documents never said.

The practical consequence: today, if a production conversational-AI system gives a customer a fabricated answer in a live chat, nothing in the live request path catches it. It would only surface if a human noticed (via a `/feedback` endpoint — see the debugging section below) or if that exact conversation pattern happened to be represented in a later offline eval run.

**Concrete recommendation for closing the gap**: take the groundedness grader that already exists in an eval-tooling service and run a cheaper, faster version of the same check synchronously in the live request path, after retrieval and generation but before the response is returned to the customer. It doesn't need to be the full LLM-judge used offline — a smaller/faster model call, or even a simpler NLI-style entailment check, scoring "is this answer supported by the retrieved context" as a single number, gated at some threshold. Below threshold, either fall back to a safer canned response ("let me have someone follow up on that") or flag the response for immediate review. This reuses eval logic already validated offline instead of inventing something new — it's an integration and latency-budget problem, not a research problem. The latency cost of one extra small model call has to be weighed against the voice-latency numbers in section 1, which is exactly why this is an ops decision, not just a product one.

### The pattern, actually implemented and running: this project's guardrails + online eval

The gap described above — "good detection tooling, but only offline" — is exactly what this project's `agent-service` and `llm-gateway` close, at three different cost/latency points, so you can see the tradeoff live instead of just reading about it:

1. **`services/llm-gateway/app/guardrails.py`** — strategy #3 (policy/safety), inline, on *every* request, before a provider is called and again before the response returns. Deliberately cheap regex/keyword checks (prompt-injection patterns, PII patterns), not an LLM call — fast enough to sit in the blocking critical path. This is the "check on every single generation" pattern that's genuinely realistic in production; a real deployment would swap the regexes for a dedicated moderation API or small classifier, but the shape (check inline → block/redact → log) doesn't change.
2. **`services/agent-service/app/online_eval.py`** — a live, running version of the *synchronous* check recommended above, except deliberately **not synchronous**: it's a sampled (`ONLINE_EVAL_SAMPLE_RATE`), asynchronous LLM-judge call, scheduled via FastAPI `BackgroundTasks` strictly *after* the response has already gone out. This is the honest middle ground between "nothing runs live" (a common real gap) and "every request pays for a blocking judge call" (the full recommendation above) — it gets you a live quality signal on live traffic without touching the latency budget of a single request. The score attaches to that request's own Langfuse trace (`Langfuse.create_score(trace_id=...)`), so it's visible next to the trace a human would already be looking at.
3. **`services/eval-service/`** — strategy #1's full offline form, unchanged from what an eval-tooling service already does today: scenario-based, on-demand, a known `success_criteria` to grade against.

Seeing all three side by side (and why none of them substitutes for the other two) is the point of the root README's "How it all works" §3 in that project — worth reading once you've internalized this section, because "which of these three should catch this bug" is a real design decision, not a settled one.

## 4. How to Debug AI/LLM Systems

"Just read the logs" works for a deterministic service because a log line usually tells you what branch of code ran and why. It breaks down for an LLM/agent system for a specific reason: once there's tool-calling or multi-agent handoff involved, a single user-visible turn might involve a retrieval step, one or more tool calls, a routing decision between sub-agents, and a final generation step — and the bug could be in any one of them. A log line saying "returned wrong answer" doesn't tell you whether retrieval pulled the wrong documents, a tool call returned bad data, the routing logic sent the request to the wrong handler, or the final generation step ignored good context it was given. You need to see the *whole chain* for that one turn, in order, with inputs and outputs at each step — that's what a trace is.

A trace is the unit of debugging for LLM systems the way a stack trace is the unit of debugging for a crash: it's the full sequence of LLM calls, tool calls, and retrieval steps that happened in service of one request, with each step's input/output captured so you can find the exact point where things diverged from what should have happened.

### A concrete example: trace_id to feedback

A production conversational-AI system can have the debugging pattern worth learning from directly: every request produces a trace in LangSmith, keyed by a `trace_id`. That `trace_id` is returned to the API client in the response — and critically, it's *reused as an input* to a `/feedback` endpoint. So the actual debugging flow looks like this: a customer or agent flags a bad response in the product UI → the UI calls `/feedback` with the `trace_id` from that exact response → that lands you directly on the LangSmith trace for that exact turn, showing the exact retrieval results, tool calls, and LLM prompts/completions that produced it. You go from "a user said this was wrong" to "here is the exact retrieved document / tool call / prompt that caused it" without guessing or trying to reproduce the conversation from scratch.

The voice side works on the same principle with different tooling: Langfuse `langfuse_trace_id` and `langfuse_observation_id` are persisted directly on `TestRun` and `AudioEvaluation` MongoDB documents, so a bad eval result or a flagged test run can be cross-referenced back to its exact trace. An internal data-engineering team's Slack bot can use a third approach — OpenTelemetry spans (`mcp.request`, `mcp.tool_call`, `mcp.claude_api_call`) exportable to Jaeger/Honeycomb/Datadog — which is the vendor-neutral version of the same idea.

**The gap worth naming**: these are commonly three separate, non-integrated systems. There's often no single dashboard where you can look up one identifier and see the trace regardless of whether the bug happened in the conversational-AI backend, a voice call, or an internal Slack bot. If you're on-call and a customer reports a bad experience, the first question you have to answer yourself is *which system produced this*, before you even know which tracing tool to open. That routing step is manual today in a lot of orgs.

**Practical debugging checklist for this class of bug**, in order: (1) get the trace ID — from the API response, the feedback record, or the MongoDB document, depending on which system; (2) open the corresponding trace in LangSmith or Langfuse; (3) walk the chain — what did retrieval return, what tools were called with what arguments, what did they return, what was the final prompt sent to the model, what did it generate; (4) identify which step diverged from expected behavior. This is almost always faster than trying to reproduce the bug by re-running the conversation, because LLM outputs aren't guaranteed reproducible even with the same input.

## 5. Baselines and Rollback for AI Systems

A **baseline**, for an AI system, should mean something specific and reproducible: a fixed combination of prompt version, model version, and configuration (temperature, retrieval settings, tool definitions), together with that combination's scores on a fixed evaluation set. The point of a baseline is that it lets you answer "is this change better or worse" with a number, against a fixed reference, rather than a vibe. Without a versioned baseline, "we improved the prompt" is an unfalsifiable claim — there's no fixed prior state to compare against, and no fixed test set the comparison ran against, so the same change could look like an improvement or a regression depending on which five example conversations someone happened to glance at.

**Rollback**, correspondingly, should mean reverting to a previously known-good *versioned combination* — flipping a registry alias or pointer back to the prior prompt+model+config version — not necessarily redeploying an entire service. In a mature setup (an MLflow model registry, or an equivalent prompt-versioning system), "roll back the prompt" and "roll back the service" are two different, independently-executable operations. That separation matters because prompt/config regressions are far more common than code regressions in an LLM system, and you don't want every prompt tweak to require a full service deployment to undo.

### The common current reality

None of this exists yet in a lot of production AI stacks. There is often no MLflow, no model registry, and no formal "baseline" concept anywhere across an org's AI systems. The closest thing to a rollback mechanism tends to be the standard Jenkins/ECS deployment rollback — redeploying a prior Docker image tag through the same CI/CD pipeline used for every other deploy. That works fine for *code* regressions, but it conflates prompt/model/config state with the entire service artifact: if a prompt change and an unrelated code change land in the same deploy, rolling back the deploy to fix the prompt also reverts the unrelated code change, and there's no way to revert just the prompt.

The sharpest illustration of what's missing is a voice-AI backend's dead fine-tuning script, which references a fine-tuned model ID ad hoc in a code comment — with zero tracked lineage of what that model was trained on, when, or what its eval scores were. If that fine-tuned model needed to be "rolled back" today, there would be no record of what the prior version even was, let alone a mechanism to flip back to it. That's the baseline/rollback gap in one concrete example: a model existed, was referenced, and left no trail.

**What closing this gap would look like in practice**: version prompts and configs explicitly (even something as simple as a `prompt_version` field checked into git alongside its eval results would be a large improvement over the current state), record each version's score against a fixed eval set at the time it's promoted, and give whatever routes traffic to a prompt/model version an indirection point (a config value, a registry alias, a feature flag) that can be flipped independently of a full service redeploy. None of the machinery for this needs to be fancy — the goal is just to stop conflating "which code is running" with "which prompt/model version is active," because today those two things can often only change together.

## 6. Quantization's Role in Production Ops

_(This section covers the ops angle only — for the underlying mechanics of what quantization does to model weights, see `01-foundational-ai-ml.md`'s model fundamentals section.)_

From an ops perspective, quantization is a lever with a clear trade: a quantized model uses less memory, runs faster, and costs less to serve, in exchange for some amount of quality loss that you cannot know in advance without measuring it. The mistake to avoid is treating quantization as a free win because the memory/cost/latency numbers look good in isolation — those numbers only tell you the resource side of the trade, not whether the quality loss is acceptable for your use case.

The correct workflow ties directly back to sections 1 and 5: **establish a baseline first** — run your fixed eval set against the current (unquantized, or currently-deployed) model and record the score. Then run the same fixed eval set against the quantized candidate. Compare the two scores directly. Only ship the quantized version if the eval score holds within whatever tolerance you've decided is acceptable for the resource savings you're getting — and that tolerance should be a deliberate decision (e.g., "up to 2 points of groundedness score for a 4x memory reduction is acceptable for this use case"), not an afterthought.

This is exactly why sections 1 (measurement), 3 (hallucination/groundedness scoring), and 5 (baselines) matter as prerequisites rather than separate concerns — without a baseline and a repeatable eval set, you have no way to know whether a quantized model is "close enough," and you'd be shipping a memory/latency win blind to whatever quality you traded away for it. Given that a typical org has no baseline concept today (section 5), it also currently has no repeatable way to validate a quantization decision before shipping one — this is one concrete case where the baseline gap has a direct, practical cost if an org ever quantizes a model for a latency/cost win (which is a very plausible next move for a voice-AI backend's scaling work specifically, given the memory pressure documented in section 1).

## 7. CI/CD for AI Systems Specifically

For deterministic code, "tests pass" is a strong, reliable signal — the same input produces the same output every time, so a passing test suite genuinely tells you the code works as specified. For LLM/agent code, that guarantee doesn't hold for three specific reasons:

- **Non-determinism**: the same prompt against the same model can produce different outputs on different runs (even at temperature 0, providers don't always guarantee bit-for-bit reproducibility). A single passing test run tells you less than it would for deterministic code.
- **Prompt drift**: a prompt change can improve behavior on the exact examples you tested and regress on the many you didn't. Unlike a code change, there's no type system or compiler to tell you a prompt edit broke something — you only find out by scoring it against a representative set.
- **Model version changes outside your control**: your provider can silently update the underlying model (or deprecate a version) without you changing a line of code. Your "tests" (evals) can start failing, or subtly regressing, from a deploy you didn't make.

What an eval-gated pipeline should look like: on every change that touches a prompt, model choice, or generation config, automatically run the eval suite against a fixed golden test set, compare the resulting scores against the current baseline (see section 5), and block the deploy if there's a regression past an agreed threshold. This is the direct AI-system analog of "run unit tests, block merge on failure" — the golden set is your test cases, the eval score is your pass/fail signal, and the baseline is what you're diffing against.

### Where a typical org stands today

This does not happen in a lot of production Jenkins pipelines. An eval service's own Jenkinsfile — the pipeline for the service whose entire job is running evals — can be a pure deploy pipeline: build → ECR → ECS → CloudFormation, with no eval-execution stage in CI at all. Evals get triggered manually or on-demand via API, completely decoupled from the deploy pipeline. In practice, this means a prompt or config change can go from commit to production without anything automatically checking whether it regressed quality — the eval tooling that could catch it exists, but nothing wires it into the path a change actually takes to reach production.

The one place a production org can have a real "must pass to merge" gate is an internal context-management service's GitHub Actions pipeline — it spins up Postgres and Redis service containers, runs `ruff` for lint, `mypy` for type checking, `pytest tests/unit` with a 70% coverage floor, then integration tests, all as required CI checks. This is a genuinely solid gate — it's just gating *regular application code*, not anything AI-specific (that context-management service is infrastructure/context-management code, not prompt/model logic). A separate internal service might enforce 100% line coverage via a `run_tests.sh` script, but run it on-demand rather than as a confirmed hard CI gate.

The useful framing here isn't "there's no CI discipline" — that context-management service's pipeline proves an org can clearly know how to build a real quality gate when it wants to. The gap is specifically that this pattern has never been extended to the thing that most needs it: nothing in the AI-specific systems treats an eval regression as a build failure the way that context-management service treats a failing unit test or a coverage drop. Building an eval-gated stage for, say, an eval service or a conversational-AI backend would mean copying a pattern already proven out elsewhere in the org (service containers + a hard threshold + a required check), just pointed at eval scores instead of `pytest` output.

## 8. SRE Practices for AI/Voice Systems

A bad LLM response mid-call is a fundamentally different incident shape than a service crash, and the standard SRE playbook doesn't map cleanly onto it. A crashed service gets restarted, an autoscaler spins up a replacement, and the incident is over from the user's perspective within seconds. A live phone call where the voice agent says something wrong, misunderstands the customer, or gets stuck can't be "restarted" — the customer is mid-conversation, on a real phone call, and there's no clean recovery action that doesn't involve either a human recovering the call live or the customer just hanging up frustrated. This changes what "incident response" needs to mean for a voice AI product: the fastest fix for a bad live response usually isn't a code deploy, it's flagging the trace for review and, if the failure mode is severe or recurring, degrading gracefully (e.g., routing to a human, or falling back to a simpler/safer response mode) faster than a normal deploy cycle would allow.

**MTTD (mean time to detect)** and **MTTR (mean time to resolve)** are the two numbers that matter for measuring how well an org handles this class of incident, and tracing infrastructure is specifically what makes MTTD fast for AI bugs. For a normal service, you detect an incident from error rates or crash logs. For an AI system, the "incident" is often a quality regression with no error at all — the request succeeded, returned a 200, and was just wrong. The only way to detect that quickly is either a live quality signal (which, per section 3, a lot of orgs don't have) or a fast path from "someone noticed" to "here's the exact trace of what happened," which is exactly what a production conversational-AI system's `trace_id`-to-`/feedback` linkage (section 4) gives you. Without that link, MTTD for a quality bug is bounded by how long it takes a human to notice, describe, and manually locate the relevant conversation — which is slow and unreliable compared to a system where the trace is one click away from the complaint.

**Zero-downtime deploys for a stateful real-time voice service** are genuinely harder than for a stateless API, and this is worth being specific about rather than waving at "just do blue-green." A typical blue-green or rolling deploy assumes you can redirect new traffic to the new version and kill old instances once they've drained — for a stateless HTTP service, "drained" means "no in-flight request," which resolves in milliseconds. For a production voice-AI backend, an in-flight unit of work is a live phone call over WebRTC/SIP that can run for minutes, holding open a LiveKit room and STT/LLM/TTS provider connections for its entire duration. You cannot simply stop routing new calls to an old instance and kill it after a short drain window — you have to wait out the actual duration of every call still in progress on it, which could be several minutes, or you drop live customer phone calls mid-conversation. A correct rollout needs explicit call-draining: mark an instance as not accepting new calls, let it keep serving the calls already assigned to it until they naturally end, and only then retire it. That's meaningfully more complex than standard rolling-deploy logic, and it's a problem specific to stateful real-time media services — most web services never have to solve it.

### The gap list, stated plainly

In a typical org's AI systems, none of the following tend to exist yet: incident-response runbooks, documented MTTD/MTTR tracking, blue-green or canary deployment automation, or chaos-engineering practice of any kind. Deployments today are often straight-line: integration → qa → staging → prod via Jenkins, gated only by a manual "environment choice" human step at the prod tag — that manual gate is the closest thing to a release-safety control that currently exists in the pipeline. This isn't a unique failing — most orgs running LLM products are at a similar maturity level on this specific list — but it is a concrete, actionable gap list rather than an abstract one: no runbooks to write from scratch, no MTTD/MTTR dashboard to build, no call-draining logic in the deploy path yet, and no chaos/fault-injection testing to validate any of it holds up under failure.

## 9. Monitoring and Observability: the Ops-Practice Side

_(For a tool-by-tool comparison of monitoring/tracing platforms, see `02-llmops-mlops-tooling.md` — this section is about what SLOs and monitoring strategy actually make sense for an AI voice product, not which vendor to pick.)_

Good SLOs for an AI voice product need to combine the reliability SLOs you'd define for any service with quality SLOs that are unique to AI systems, because a system can be fully "up" by traditional standards while quietly getting worse at its actual job. A reasonable set, using the numbers above as anchors: **P95 end-to-end per-turn latency under some fixed threshold** (using a voice-AI backend's existing instrumentation — a natural target would be whatever threshold keeps a phone conversation feeling responsive, tracked against the real P95 the current ~20-calls-per-box architecture produces today, so the scaling redesign in section 1 can be judged against a concrete SLO rather than just "seems faster"); **uptime/availability**, the standard SRE metric, unchanged; and critically, **eval pass-rate above some fixed threshold** as an ongoing production SLO, not just a pre-deploy check — e.g., "groundedness score on a rolling sample of live conversations stays above X%." That third one is the one most orgs skip, and it's the one that would have caught the exact gap described in section 3.

The reason "logs only" — which tends to be the default observability approach everywhere except in a system like an internal data-engineering team's Slack bot (which can use OpenTelemetry spans instead) — isn't sufficient here comes down to what a log line can and can't tell you. Logs are built for events: "request received," "error thrown," "response sent." They're excellent at telling you something happened and roughly when. They are not built to answer "is conversation quality slowly degrading" or "did that prompt change 3 days ago make groundedness worse," because that requires aggregating a *score* across many requests over time and watching a trend — which is a metrics-and-tracing problem, not a log-search problem. A logging SaaS platform (a typical org's default logging tool) can tell you a request failed; it cannot tell you that 15% more responses this week were ungrounded than last week, because "ungrounded" isn't a thing that shows up in a log line at all unless something is specifically computing and emitting that score. That's the structural reason Langfuse/LangSmith-style tracing plus a real metrics layer (Prometheus/Grafana-style time series, not just searchable text) matters specifically for AI systems: the failure mode you're trying to catch — quality drifting down gradually, not a sharp error spike — is invisible to log search and only visible to something tracking a quality metric as a time series with alerting on the trend, the same way you'd alert on P95 latency creeping up rather than waiting for a hard outage.

## Try it yourself

Reading about these gaps is one thing; this project is built specifically to let you practice closing them without needing access to any real production system. It includes a chaos/latency-injection toggle (so you can watch what a slow-provider or dropped-tool-call failure actually looks like in a trace, and practice diagnosing it the way section 4 describes), an eval-gated CI pipeline example (a working version of the "block deploy on eval regression" pattern described in section 7, which a lot of orgs' current Jenkins pipelines don't have), Prometheus+Grafana dashboards (a concrete example of the metrics-plus-tracing setup described in section 9, as opposed to logs-only), and a baseline/rollback demo using MLflow model aliasing (a working version of the versioned-baseline-and-alias-flip rollback described in section 5, in place of the redeploy-an-old-Docker-image approach many orgs use today). Work through it in the same order as this document — measurement, latency, hallucination detection, debugging, baselines, CI gating, then SRE/monitoring — since each later exercise assumes the instrumentation from the earlier ones is in place.
